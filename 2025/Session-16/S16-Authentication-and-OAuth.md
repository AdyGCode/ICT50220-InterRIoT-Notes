# Overview of Authentication & Authorisation


## 🔐 **Authentication**

**What it is:**
Authentication is about **proving who you are**.

**Example:**
When you log into Instagram with your username and password, you're authenticating yourself — you're proving to Instagram that *you* are the owner of that account.


## 🛂 **Authorisation**

**What it is:**
Authorization is about **what you're allowed to do** after you've authenticated.

**Example:**
Once you’re logged into Instagram (authenticated), authorization determines whether you can edit your profile, access DMs, or manage someone else's page (if you’re part of a team).

## 🧠 **Remember:**

* **Authentication** = *"Who are you?"*
* **Authorization** = *"What can you do?"*

---

## Ways to Authenticate

There are many different ways to authenticate a user, here are six for you:

### 🔑 **Username and Password (Traditional Login)**

**How it works:**
User enters a unique username/email and a secret password to log in.

**Example:**
Most websites with a login form — e.g., Reddit, eBay.

✅ Pros: Simple, widely understood
❌ Cons: High risk if passwords are reused or leaked



### 📱 **Multi-Factor Authentication (MFA or 2FA)**

**How it works:**
Combines two or more authentication factors — like a password **plus** a one-time code sent to your phone or generated by an app.

**Example:**
You enter your password, then a 6-digit code from Google Authenticator or SMS.

✅ Pros: Much more secure
❌ Cons: Slightly more effort for users



### 🧬 **Biometric Authentication**

**How it works:**
Uses something **you are**, like your fingerprint, face, or voice.

**Example:**
Unlocking your phone with Face ID or fingerprint scan.

✅ Pros: Super quick and convenient
❌ Cons: Needs hardware support; privacy concerns



### 🧾 **Magic Links (Email-Based Login)**

**How it works:**
You enter your email, and the system sends you a link. Clicking the link logs you in — no password needed.

**Example:**
Notion and Slack offer this as an option.

✅ Pros: No passwords to remember
❌ Cons: Relies on email security



### 🧠 **Single Sign-On (SSO)** (Non-OAuth variants)

**How it works:**
Authenticate once with a trusted identity provider (like Active Directory or SAML), and get access to multiple systems.

**Example:**
A university login that gets you into Gmail, Zoom, and the student portal all at once.

✅ Pros: Seamless access to multiple services
❌ Cons: Complex to set up and manage



### 🔗 **OAuth** Open Authentication

**What it is:**
OAuth is a protocol (a set of rules) that lets you **let other apps access some of your data without giving them your password**.

**Example:**
You’ve probably used the “Log in with Google” or “Log in with Facebook” button. That’s OAuth in action. It lets websites or apps use your Google/Facebook account to log you in or get access to your data (with your permission).

🔐 You keep your password secret — but still grant access safely.


#### ⚙️ **OAuth 1.0 vs 2.0 vs 2.1** (Table Comparison)

| Feature                           | OAuth 1.0              | OAuth 2.0                            | OAuth 2.1 (Draft)                           |
| --------------------------------- | ---------------------- | ------------------------------------ | ------------------------------------------- |
| Release Year                      | 2010                   | 2012                                 | Ongoing (2020 draft, not final)             |
| Token Type                        | Signed tokens          | Bearer tokens (simpler, less secure) | Bearer tokens                               |
| Security                          | More secure by default | Requires HTTPS to stay secure        | Improved security defaults                  |
| Complexity                        | Complex (crypto-heavy) | Simpler to implement                 | Same as 2.0 but less room for bad practices |
| Client Types                      | Mostly server apps     | Supports mobile, web, server apps    | Same as 2.0                                 |
| Refresh Tokens for Public Clients | Not common             | Supported                            | Recommended security practices enforced     |
| PKCE Support                      | No                     | Optional                             | Required for public clients (e.g., mobile)  |
| Implicit Flow                     | Yes                    | Yes (deprecated)                     | Removed                                     |

✅ **TL;DR**:

* OAuth 1.0: Secure but hard to implement
* OAuth 2.0: Easier, but can be insecure if done wrong
* OAuth 2.1: Cleaner version of 2.0 with safer defaults


#### 🛠️ **Options for Implementing OAuth as a Server (in Python)**

If you're building an app **that lets others log in using OAuth (like Google or Spotify)**, these tools help you create the server side:

| Tool/Library             | Description                                                                  |
| ------------------------ | ---------------------------------------------------------------------------- |
| **Authlib**              | Modern, flexible, supports OAuth 1/2 — great for building full OAuth servers |
| **OAuthLib**             | Lower-level OAuth library — used under the hood by other tools               |
| **FastAPI + Authlib**    | Great combo — Authlib integrates smoothly with FastAPI                       |
| **Django OAuth Toolkit** | For Django apps — provides OAuth2 provider support                           |


#### 🌐 **Options for Implementing OAuth as a Client (in Python + FastAPI Website)**

If your FastAPI app wants to **let users log in with Google, GitHub, etc**, these tools make it easier:

| Tool/Library                | Description                                                        |
| --------------------------- | ------------------------------------------------------------------ |
| **Authlib**                 | Powerful and easy — supports OAuth clients for all major providers |
| **Requests-OAuthlib**       | Simple, good for scripts or backends                               |
| **FastAPI Users + Authlib** | Plug-and-play user management + OAuth for FastAPI                  |
| **Social-auth-core**        | Can be used with various frameworks, including custom setups       |

📦 **Example OAuth flow in FastAPI using Authlib**:

1. User clicks "Login with Google"
2. Your app redirects them to Google
3. User logs in and gives permission
4. Google redirects them back to your site with a code
5. Your app exchanges that code for access tokens
